## What v3 changes

v3 keeps the same answers and output format, so parsing and scoring are unchanged. The rules are `TURN_GUIDE_V3` and `CALL_GUIDE_V3` in `annotate.py`. The version for people is `human_check/GUIDE_v3.md`.

**Turn ends**
- **Split the request into its parts first.** Every part needs a successful call or output behind it.
- **Run check 1 first,** even when a part is also missing.
- **Name the evidence before choosing `unsupported_claim`:** the claimed value, plus the output that contradicts it or the call that is missing.
- **Unseen earlier detail is not a false claim.** The annotator sees only this turn's calls, so detail that may come from an earlier turn doesn't count.
- **Check the arguments of every call that changes something, even when the closing message is accurate.** A name or condition the agent chose itself is `should_ask_user`. A direct mapping of the user's words, such as "top priority" to the top number, is not.
- **Giving up when the fix was visible is `missing_action`.** That covers an error that names the fix, or a needed tool shown in the trace. Saying "no tool can do it" is `done` only when nothing visible contradicts it.
- **Imperfect content in a part that was done is not missing.**

**Calls**
- **First decide whether the step changes anything.** Overwriting a file with empty content is a change. A call to a tool that changes state is a change even with an amount of zero.
- **The plan does not make a change requested.** Compare each change with the latest request.
- **Repeating a change that already succeeded in this turn is an unrequested change.** So is deleting something the request didn't ask to change, even a file the agent made by mistake.
- **These are on track:** intermediate steps toward the requested end state, and retrying a call that failed.
- **Trust the evidence list,** which code builds from the whole trace. Only a value marked `nowhere` can be made up, even a name the agent invented earlier.
- **A step with no arguments is never made up.**

## Second look at the 7 doubtful pilot steps

On H028, H038, H056, H065, H079, H092 and H098, both annotators disagree with the consensus. A second blind pass labelled these 7 steps again from `GUIDE.md`, without the consensus or the annotators' answers in view. **It sided with the annotators on all 7.** These are genuinely ambiguous steps on which the two labellers leaned one way.

The consensus is left as recorded, because changing the answer key after seeing the annotators' answers would bias the check in their favour. Instead, this table shows how much the pilot's deciding number depends on these 7 steps:

| The second pass's answer on all 7 | 0.57 | 0.78 |

(Kappa, reweighted, every step, problem vs fine.)

**The pilot verdict holds in every version.** Annotator A stays below 0.6, so the guide rewrite stands.

## Rule decisions (taken 30 Oct 2026, open to team objection)

| # | Rule | Steps | Decision and reason |
|---|---|---|---|
| 1 | A call to a tool that changes state is a change even with an amount of zero | H079 | **Reversed from the first v3 draft.** The v2 wording, both annotators and the second pass agree, and the rule is simpler to apply. |
| 2 | Deleting or overwriting something the request didn't ask to change is off track, even a file the agent made by mistake | H092 | **Reversed from the first v3 draft**, for the same reasons. |
| 3 | A name or condition the agent picks for a change is `should_ask_user`, even when it fits the request | H056, H065 | **Kept, but contested.** It matches BFCL's missing-parameter design, where the right move is to ask. Both annotators and the re-check disagreed under v2. v3 now states the rule outright, so annotators can follow it. |
| 4 | A value marked `nowhere` is made up even if the agent invented it in an earlier call | H027 | **Kept.** It matches the code-built evidence list the classifier sees. |
| 5 | Imperfect content in a part that was done is `done` | H033 | **Kept.** Format quality is not drift or a false claim. |

v3 also says that asking the user for a value a request already gave is `missing_action`. That settles H028, where Annotator B pointed out the request already said "travel insurance".

## v3 result (run 30 Oct 2026)

Both annotators relabelled the 200 checked steps with guide v3, the same two annotators as under v2. Annotator B left 2 answers unreadable, and those 2 were redone.

The new labels are `runs/data/q9b_s1t_49146/val/annot_v3_{deepseek,glm}.jsonl.gz`, with logs beside them.

| **val2, fair test:** consensus vs Annotator B | 0.66 | **0.71** |

| **All 200 steps:** consensus vs Annotator B | 0.62 | **0.71** |
| All 200 steps: Annotator A vs Annotator B | 0.66 | 0.76 |

**Verdict by the proposal's rule.** On the fresh sample the weaker annotator is B, at 0.71. That passes the 0.7 bar but sits in the 0.6 to 0.8 band, where the rule says to label more steps until the result is clear. Annotator A alone is above 0.8.

**Remaining weak spot: false claims at turn ends.** On val2, the kappa there is 0.46 for Annotator A and 0.38 for Annotator B. False claims are rare, a handful per 50 turn ends, so these numbers are noisy. But false claims are half of the primary metric, so they matter most.

**Next, in order:**
1. **Label more steps.** The next 100 come from the 9B test passes once they exist, as the proposal plans, with the same protocol.
2. **If false-claim agreement stays low, add a third annotator for closing messages.** It would settle the cases where A and B disagree on false claims.
3. **Relabel all val and train with v3** before Laya is retrained on annotator labels. That is about 1,770 steps per annotator on val alone, so check with Pavan first.

## How to run v3

This needs the key set in `OPENCODE_KEY` and an unpacked val run folder: the states, steps and labels files, not `.gz`. The script resumes and skips steps already in the output file, so both samples can go into one file.

```
RUN=<unpacked runs/raw/q9b_s1t_49146/val>
OUT=runs/data/q9b_s1t_49146/val
for M in deepseek-v4.1-flash glm-5.3-flash; do                # Annotator A, Annotator B
  F=$OUT/annot_v3_$(echo $M | cut -d- -f1).jsonl          # annot_v3_deepseek.jsonl, annot_v3_glm.jsonl
  OPENCODE_KEY=... python analysis/annotate.py $RUN $M $F --guide v3 --uids human_check/val2/key.json  --conc 16
  OPENCODE_KEY=... python analysis/annotate.py $RUN $M $F --guide v3 --uids human_check/pilot/key.json --conc 16
done
python human_check/score.py human_check/val2  --guide v3   # the fair test: val2/results_v3.md
python human_check/score.py human_check/pilot --guide v3   # optimistic, v3 was written here: pilot/results_v3.md
```

**Reading the val2 v3 result** with the proposal's rule, on the weaker annotator:
- **0.8 or more:** passes. Relabel all val and train with v3 and use those labels.
- **0.6 to 0.8:** label more steps. The test-run sample is next.
- **Below 0.6:** rewrite again from the val2 disagreements.

Drop `--uids` to relabel all 1,772 val steps. Training on annotator labels needs that full relabel.

## Code changes in this round

- `analysis/annotate.py`: guide v3 rules, plus `--uids` to label only the steps listed in a `key.json` or a uid file.
- `human_check/score.py`: `--guide` picks which annotator labels to score. The default is v2, as before. Other versions are written to `results_<guide>.md`, and results are now written as UTF-8.
- `human_check/GUIDE_v3.md`: the version of v3 for people. `GUIDE.md` stays as v2, the record of the pilot round.
- `human_check/val2/`: the fresh sample, both checkers' sheets, the referee's decisions, and results against the v2 and v3 annotator labels.
